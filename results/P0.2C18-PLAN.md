# FASTIWM P0.2C18 plan

P0.2C17 is the first experiment to prove that the routed IIgs IWM receives
ready bytes from the private 2-us transmission. It captured `$80` followed by
seven `$FF` bytes. Since the firmware deliberately begins with sixteen `$FF`
sync bytes, this is consistent with initial framing followed by the intended
preamble.

The remaining host receiver was structured like ordinary application code:
every byte called `ReadIWMByteC`, loaded a fresh 16-bit timeout, returned, and
then ran the marker or payload loop. A 2-us IWM byte occupies only 16 us. The
Apple 3.5-inch reference instead demonstrates consecutive inline `LDA Q6` /
`BPL` polling and warns that the host must keep pace with every byte.

P0.2C18 changes only this hot path:

- marker `$D5 $AA $96` polling is inline;
- the 512-byte capture loop polls and stores inline;
- timeout protection remains at every wait state;
- exact IWM mode `$0F`, internal Slot 6, `DISKREG $40`, READY triggering, and
  payload validation are unchanged;
- the already-flashed P0.2C14 firmware remains the paired transmitter.

The expected result is `FAST PASS: exact 512-byte 2us payload verified.`
