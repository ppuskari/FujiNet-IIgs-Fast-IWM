# P0.2D8 station-handoff control recovery experiment

P0.2D7 fixed the interrupt-watchdog and GS/OS return-path failures. During a
later station change, the IIgs reported `error=$0001 provider=$0000`. That
combination is a host SmartPort call carry with no FujiNet provider error.
The provider log showed that the new station had started and delivered PCM
before the client disconnected, so this is a control-path recovery test, not
a change to the proven 2-us payload loop.

P0.2D8 changes the matched pair as follows:

- The IIgs retries idempotent START, STATUS, and pre-trigger ARM calls up to
  eight attempts, one 60-Hz tick apart. DOC playback and its 512-KiB source
  ring remain active during the bounded retry window.
- A terminal failure reports the underlying SmartPort error and the total
  retry count instead of only the collapsed `$0001` category.
- FujiNet keeps TCP connection failures in the reconnecting state rather than
  reporting a terminal provider state after one refused reconnect.
- FujiNet reconnects after 250 ms while retaining queued PCM, and reports
  disconnect, reconnect, duplicate ARM, ISR, and heap telemetry.
- P0.2D7's duplicate-READY ISR guard and full IIgs route restoration remain
  unchanged.

## Test sequence

1. Deploy the matched P0.2D8 firmware and host only after the current P0.2D7
   stream has been stopped.
2. Confirm normal buffering/playback and a stable `FASTIWM D8 HEAP` report.
3. Make several ordinary station changes, including closely spaced changes.
4. If recovery occurs, capture `PROVIDER LOST`, `PROVIDER CONNECTED`, and
   `CONTROL RETRY` serial lines and confirm playback continues.
5. If the IIgs stops, record all three fields: `error`, `provider`, and
   `smartport`, plus `retries`.
6. Quit normally and confirm GS/OS returns without a `$C600` monitor break.
