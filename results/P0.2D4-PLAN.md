# P0.2D4 corrected SPI-provider wait

P0.2D3 proves the application endpoint handoff and TCP buffering work:

- FujiNet accepted `192.168.5.235:22510` from the IIgs;
- the provider connected and supplied more than 100 KiB;
- the PSRAM FIFO reached 35,808 bytes after the first packet was popped;
- the 32-packet batch armed and the READY edge triggered.

The first waveform failed because P0.2D2 changed
`spi_device_acquire_bus()` to a 100 ms finite timeout. This ESP-IDF driver
supports only `portMAX_DELAY` and rejected the call immediately.

P0.2D4 restores `portMAX_DELAY`, the same bus-acquisition contract used by
the proven C19 and D0 burst transmitters. D3's application host/port prompt,
the D3EP WRITEBLOCK, PSRAM FIFO, and D2 reset-free successful batch return
remain unchanged.

Expected first-batch trace:

```text
FASTIWM D4 ENDPOINT SET host=192.168.5.235 port=22510 source=IIgs
FASTIWM D4 PROVIDER CONNECTED ...
FASTIWM D4 PROVIDER BATCH ARMED packets=32 pcm=16384
FASTIWM D4 READY TRIGGER ...
FASTIWM TX START packet=0 ...
FASTIWM TX DONE packet=31 ... err=0
FASTIWM D4 PROVIDER BATCH DONE batch=1 packets=32 ... err=0
```
